# 单功能迭代文档

本目录保存每轮敏捷开发的唯一事实记录。模拟演练不创建迭代文档，也不改变正式 Backlog 状态；真实开发时，必须在编码前创建并由用户确认对应文档。

## 文件命名

```text
docs/iterations/<featureId>-<英文短名称>.md
```

例如：

```text
docs/iterations/F-001a-app-shell.md
```

功能拆分后使用稳定的切片 ID。不要用父功能 ID 混记多个可独立验收的切片，也不要因为排序变化而修改 ID。

## 文档生命周期

1. 介绍当前关注层的规划、进度和可立即开始项，由用户选择本轮功能或切片；关注层由用户决定，未指定时默认建议编号最小且仍有未完成项的层；
2. 创建迭代文档并写入功能说明；
3. 讨论并确认本轮最小技术方案；
4. 讨论并确认最小 happy path（正常成功路径）测试；
5. 三部分全部确认后开始开发；
6. 实现中若产品行为、范围或关键技术路线发生变化，更新同一份文档并重新确认；
7. 实现后记录实际改动和真实自动验证；
8. 用户人工验收后记录结论和日期；
9. 更新切片、父功能和依赖层状态；
10. 提交和 push 分别等待用户明确授权，本轮结束后由用户决定下一项。

## 状态口径

- `未讨论`：尚未进入单功能设计；
- `设计中`：正在确认功能说明、技术方案或 happy path；
- `待实现`：迭代文档已经确认，但尚未开始编码；
- `实现中`：正在编码或自动验证；
- `待人工验收`：实现和约定的自动验证已经完成；
- `已验收`：用户已经明确确认通过；
- `待修改`：人工验收未通过或实现中发现必须修正的问题；
- `继承草稿`：基线中已有实现，但尚未按本产品规则完成讨论、测试和人工验收；
- `部分完成`：父功能已有部分必要切片通过，但仍有必要切片未验收。

代码存在、界面可见、基础接线可用或继承测试存在，都不能把“继承草稿”自动提升为“已实现”或“已验收”。只有全部必要切片通过人工验收，父功能才可以标记完成。

## 最小模板

```markdown
# <featureId>：<功能名称>

> 状态：设计中
> 父功能：<父功能 ID 与名称；没有则写“无”>
> 前置依赖：<已满足的直接依赖；没有则写“无”>

## 1. 功能说明

### 1.1 目标

<本轮要产生的用户可观察结果。>

### 1.2 本轮范围

- <本轮明确提供的行为。>

### 1.3 不在本轮范围

- <容易被误带入但本轮明确不做的内容。>

### 1.4 状态变化

- <验收通过后切片、父功能及相关草稿状态如何变化。>

## 2. 本轮技术方案

<只记录实现本轮功能所需的最小方案、关键边界与失败处理，不提前冻结完整架构。>

## 3. 最小 happy path 测试

<写明前置条件、操作步骤、可观察结果和通过条件。>

## 4. 实现与验收记录

<开发前不填写。实现后记录实际改动、真实命令及结果、已知问题、人工验收结论和日期。>
```

模板中的尖括号是使用说明，创建具体迭代文档时必须替换，不得把占位内容提交为已确认设计。
