## 2. 产品目标

Agentic Markdown 的 MVP 是一款面向 macOS 的高性能、本地优先、多文档 Markdown 桌面 App。用户能够在一个窗口中组织多个任意目录和独立 Markdown 文件，以阅读、编辑或源码模式处理文档，并安全地把修改保存回原文件。

MVP 的核心价值是：

- 多文档查看和编辑体验清晰、连贯；
- 本地 `.md` 与 `.markdown` 文件始终是正文唯一真源；
- 核心能力完全离线可用；
- 性能从每项功能开始持续观察和改善；
- 不以私有文档数据库、完整 WYSIWYG 或 Agentic 能力换取实现便利。

## 3. MVP 用户故事

1. 作为本地 Markdown 用户，我希望直接打开一个文件并开始阅读或编辑，而不必先建立项目或导入数据库。
2. 作为同时维护多个目录的用户，我希望把多个任意目录与独立文件放进同一窗口，并明确看出它们的顶层归属。
3. 作为写作者，我希望在编辑模式中直接修改 Markdown 原文，同时获得即时排版反馈。
4. 作为高级用户，我希望随时通过快捷键进入源码模式，精确查看和编辑全部 Markdown 标记。
5. 作为阅读者，我希望使用独立阅读模式和阅读主题查看规范渲染结果。
6. 作为多文档用户，我希望通过主区标签与右侧副区同时处理多篇文档，而且同一文档不会重复出现。
7. 作为文件所有者，我希望保存成功与失败都清晰可判定，并且任何失败都不会把原文件变成半个文件。
8. 作为会同时使用外部工具的用户，我希望 App 识别外部修改、重命名和删除，并在发生冲突时保留我的未保存内容。
9. 作为经常处理大文档和大目录的用户，我希望界面优先保持可交互，扫描、索引和重型渲染不会无故阻塞当前工作。
10. 作为中文用户，我希望中文输入法的候选、确认、取消和撤销不被 Markdown 补全或装饰打断。
11. 作为键盘用户，我希望核心流程都能用键盘完成，拖放和分隔线操作也有等价入口。
12. 作为重视隐私的用户，我希望文档、搜索词和完整路径不会被上传，远程图片也不会默认请求。
13. 作为重视可移植性的用户，我希望卸载 App 后仍能用其他编辑器直接打开原有 Markdown 文件。

## 4. MVP 范围原则

### 4.1 正向范围

- 首发平台为 macOS，界面语言为简体中文；
- 支持 `.md` 与 `.markdown`，不支持 `.mdx`；
- 支持独立文件、多目录工作区、文件树、多标签和左右主副区域；
- 支持阅读、编辑、源码三种文档级模式；
- 支持 CommonMark、GFM 和已经确认的内建扩展；
- 支持手动保存、可选自动保存、外部变化处理、冲突处理和崩溃恢复；
- 支持文内查找、Quick Open 和当前窗口全文搜索；
- 支持主题、字体、排版与主区正文缩放；
- 支持必要的安全、权限、数据一致性和性能观察能力。

### 4.2 明确不进入 MVP

- Agentic、插件、脚本、MCP、Local HTTP API；
- Windows、Linux、Web、移动端和多窗口；
- 完整 WYSIWYG、源码与阅读并排、任意递归分栏、同文档多视图；
- 未命名文档、Save As、App 内重命名和磁盘移动；
- 失焦保存、Markdown 自动格式化、矩形/列选择；
- Wikilink、Backlinks、标签系统、Daily Notes、任务汇总、图谱、Canvas；
- Hover 内容预览、PDF/网页嵌入、打印和文件级导出；
- 字数/字符数/阅读时间、常驻状态栏和用户可配置的内容宽度；
- Git 操作、官方同步、多人协作、评论、分享和发布系统；
- 图片资产清理、全工作区替换、正则搜索和自定义快捷键；
- Mermaid 之外的 Graphviz、ECharts、PlantUML 等图表渲染；
- 因文件整体较大而自动切换模式或整篇关闭功能；
- Screen Reader 完整支持、高对比度、Reduced Motion 和 UI 多语言。

其中，网络盘和可移动磁盘在 MVP 中只能作为普通目录尝试使用，不宣称正式支持；外部同步目录也只按普通本地目录处理。

### 单功能流程

每轮由用户从当前 Backlog 中指定下一功能。完整流程为：

1. 介绍当前关注层的整体功能规划，以及范围确认、讨论、文档、实现、自动验证和人工验收的当前进展；
2. 列出该层未完成且前置依赖已经满足的功能，给出选择建议和理由，由用户决定本轮功能；
3. 根据功能实际复杂度决定整项实现或拆成多个切片；
4. 讨论并确认该轮功能行为和边界；
5. 在 `docs/iterations/<featureId>-<英文短名称>.md` 创建本轮唯一的单功能迭代文档；
6. 依次确认功能说明、当前轮最小技术方案和最小 happy path 测试；
7. 文档确认后开始开发，不默认采用 TDD（Test-Driven Development，测试驱动开发）；
8. 实现中若产品行为、范围或关键技术路线变化，先更新同一份文档并重新确认；
9. 实现后运行该轮约定的真实自动验证，并记录实际改动、命令和结果；
10. 由用户人工确认通过，记录验收结论和日期，更新切片、父功能及层级状态；每轮新增或变更功能同步维护[产品功能手册](./product-feature-manual.md)，实现后先标注待验收，人工通过后更新为已验收；
11. 提交和 push 分别等待用户明确授权；本轮结束后再由用户选择下一项。

异常路径、安全测试、专项性能测试和临时 PoC 不做全局预设，在涉及具体功能时结合风险单独决定。

模拟演练可以按用户要求跳过实现，但模拟结果、假设命令和模拟验收不得写入正式迭代记录，也不得改变 Backlog 状态。

## 15. MVP 完成定义

MVP 是否完成不由单一数字或一次性技术方案决定。满足以下条件后，才可以提议进入 MVP 发布确认：

- 所有仍属于 MVP 的可交付 Backlog 项均已完成或经用户明确移出 MVP；F-002 等持续约束须对本次发布范围具备验证证据，不能仅以规则已写入文档视为通过；
- 每项已完成能力都经过当轮自动验证和用户人工验收；
- 所有待专项设计项已经解决或由用户明确调整范围；
- 本地 Markdown 仍是正文唯一真源，核心流程离线可用；
- 已知实现没有把明确非 MVP 或永久不提供的能力带入产品；
- 发布形态、目标 macOS 环境和当时需要的最终验证由用户另行确认。
